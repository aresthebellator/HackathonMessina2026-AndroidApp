## Doctrine

**Microcopy is documentation-grade, never marketing-grade.** Every word in the interface is documentation: it tells the user what is true and what to do. The bar is a good technical doc — plain, specific, calm — not a launch announcement. Marketing-speak ("exciting opportunities", "we're thrilled"), fake cheerfulness, and emoji used to paper over an unclear message are all the same failure: tone substituting for information. An emoji never rescues a sentence that does not say what happened. The test for any string is not "does it sound friendly" but "after reading this, does the user know the true state and the next action". Anchor user-language, real-world phrasing to Nielsen H2 via `design-judgment-references` — do not restate the heuristic from memory.

**An error that does not say what and what-next is a non-message.** Every error message has exactly one mandatory structure: `[What's wrong]. [What to do].` The first sentence names the specific cause in the user's terms; the second names the concrete action the user can take now. `"Something went wrong"` carries zero information — it states only that an error exists, which the user already knew from the failure. `"Oops! Something went wrong 😬"` is the same non-message wearing a costume. A message that the user cannot act on is a logged exception leaked to the UI, not a designed error. This is Nielsen H9 (help users recognise, diagnose, and recover from errors) — cite it through `design-judgment-references`, do not paraphrase it from memory.

**Formatting is correctness, not polish.** A mis-rendered value is a bug with the same severity as a wrong value, because to the user it *is* a wrong value. Money is always rendered with locale grouping and an explicit currency — never a bare float; `12.5` shown as a price is the generalised djmoney-class bug (a raw numeric type leaking to the UI because no money/locale formatter sat between the model and the screen) and it is a defect, not a nitpick. Numbers are digit-grouped per locale. Dates and times are user-facing and localised — a raw ISO timestamp (`2026-05-18T00:00:00Z`) rendered as UI text is a bug. Quantities carry their unit. "It's just `12.5`, formatting is polish" is precisely the rationalisation that ships the bug. If you cannot confirm a value's real type or the user's locale, that is a data-shape question owned by `grounding-before-designing` — flag it, do not guess a format onto an unknown type.

**Destructive-action confirmation is proportional to blast radius — both directions fail.** The friction of a confirmation must scale to what is irrecoverably lost. Trivial and undoable (reorder a list, archive with undo) → no modal; an inline action or an undo affordance. Significant or irreversible (delete one record permanently) → an explicit confirmation that *names what is lost*, not a generic "Are you sure?". Catastrophic or wide-blast (delete an account, wipe many records) → typed/explicit confirmation that forces deliberate intent. Under-confirming destroys data silently; over-confirming — a dialog reflexed onto every action "to be safe" — trains users to dismiss confirmations without reading, which destroys the next real one. A blanket confirm policy is not caution; it is the over-confirming failure.

**Ownership seam — words and formatting here, state existence elsewhere; hold it in both directions.** This skill owns **what every state, label, number, and message SAYS and how it is formatted** — the content itself. It does **not** own **which states or screens exist**; that is owned by `designing-states-not-screens`. The seam is content-existence vs content-itself: that an empty state exists is a state-design decision (theirs); the headline, body, and CTA wording inside it are this skill's output. Never silently expand into deciding that a state or screen should exist ("while I'm here I'll add an empty state") — that usurps `designing-states-not-screens`. Conversely, never accept drafted words from that skill as settled — provisional or labelled "handoff hint", the words are produced here. Both failures are real and the seam is held from this side: you write the words for the states you are handed; you do not invent the states.

## Process

1. **Inventory every content surface in scope.** Locate each piece of text, each number, each money value, each date/time, each quantity, and each destructive action on the surfaces you were handed. One pass, exhaustive — an unlisted string is an unreviewed string.
2. **Confirm you were handed states, not asked to invent them.** Verify the set of states/screens is already decided (by `designing-states-not-screens`). If a needed state does not exist, raise it as that skill's decision — do not create it here. This is the seam check, done first so it cannot be skipped.
3. **Rewrite all copy to documentation-grade.** Make every string plain, specific, and calm: strip marketing-speak, fake cheerfulness, and tone-fix emoji. Rewrite every error to `[What's wrong]. [What to do].` with a specific cause and a concrete next action. Verify against Nielsen H2 and H9 via `design-judgment-references`.
4. **Apply correct formatting to every value.** Money → locale grouping + explicit currency, never a raw float. Numbers → locale digit grouping. Dates/times → localised, user-facing, never raw ISO. Quantities → with units. For any value whose real type or the user's locale you cannot confirm, flag it and defer the data-shape question to `grounding-before-designing`; do not guess.
5. **Set each destructive action's confirmation to its blast radius.** Classify every destructive action as trivial/undoable, significant/irreversible, or catastrophic/wide-blast, and apply the proportional confirmation (undo/inline, explicit confirm naming what is lost, or typed confirmation). Reject both no-confirmation on irreversible actions and blanket confirmation on trivial ones.
6. **Final seam check.** Confirm you produced only words and formatting for the states you were handed, and did not decide that any state or screen should exist. If you did, remove it and return that decision to `designing-states-not-screens`.

## Red flags

| Rationalisation | Reality |
|---|---|
| "`Oops! Something went wrong 🙈` is friendly enough." | Friendly is not clear. An error that names neither what is wrong nor what to do next is a non-message; the emoji is tone covering for absent information. Rewrite to `[What's wrong]. [What to do].` and verify against Nielsen H9 via `design-judgment-references`. |
| "It's just `12.5`, the formatting is polish — ship it." | A raw float shown as money is the djmoney-class bug: a wrong value to the user, same severity as a wrong number. Locale grouping plus explicit currency, or it is defective. Formatting is correctness, not polish. |
| "This date as `2026-05-18T00:00:00Z` is fine, users will get it." | A raw ISO timestamp in the UI is a leaked machine type, not a date the user reads. Localised, user-facing date/time or it is a bug — same class as the raw-float money defect. |
| "I'll add a confirm dialog to every action to be safe." | Blanket confirmation is the over-confirming failure: it trains users to dismiss dialogs unread and so disarms the next real one. Confirmation is proportional to blast radius — undo for trivial, explicit naming-what-is-lost for irreversible, typed for catastrophic — never uniform. |
| "Deleting is fast and common, skip the confirm to keep it snappy." | An irreversible delete with no confirmation destroys data silently — the under-confirming failure. Speed does not outrank an unrecoverable loss; name what is lost before it is lost. |
| "While I'm here I'll add an empty state too / a new error screen." | Whether a state or screen exists is owned by `designing-states-not-screens`. This skill owns the words and formatting inside it, not its existence — inventing the state here usurps the other skill and breaks the seam. |
| "The other skill already sketched the headline, I'll just keep it." | Provisional or "handoff hint" or not, the words are this skill's output. Take the state's job from `designing-states-not-screens`; write the words here. Accepting their draft as settled blurs the content-existence vs content-itself seam. |
