## Doctrine

**Motion communicates intent, or it is decoration — and decoration is cut, not kept.** This is the line between a UI that passes the heuristics and one that feels category-defining. Every animation, transition, and async affordance must answer one question: *what state change or system status does this make legible?* An element appearing answers "this is new"; a row sliding out answers "this is gone"; a control depressing answers "your input registered"; a skeleton answers "this region is loading, and here is its shape". Motion that cannot name what it tells the user is not polish — it is the most common counterfeit of polish. It is the Rauno test: motion that explains nothing is a slop tell, not a craft tell. Anchor any contested motion-or-depth call to `design-judgment-references` (Rauno — interaction polish: motion must explain a state change; decorative motion and incoherent depth are the failure). This skill stays in its lane: it does not own *which* states exist (`designing-states-not-screens`), nor the words (`precision-copy-and-formatting`), nor static hierarchy (`visual-hierarchy-and-type`). It owns how the UI *behaves and moves between* those states.

**Perceived performance is a design decision, not an engineering afterthought.** The number that matters is the felt one. An optimistic update that reflects the user's action instantly, an affordance that acknowledges the press in the same frame, a skeleton that shows the shape of what is coming instead of a spinner that shows nothing — these are designed choices about what the user *experiences* while the system works, made independently of how fast the system actually is. Treating latency as "the backend's problem" and bolting on a spinner at the end is the abdication this doctrine names. The spinner-vs-skeleton-vs-optimistic question is a perceived-performance design call with a stated reason, every time.

**Optimistic vs pessimistic is a deliberate, stated, justified choice — and this is the non-negotiable core.** This skill is flexible in *how* you reach an interaction design; it is not flexible on this. Every async action either reflects success before the server confirms (optimistic) or waits for confirmation (pessimistic), and which one is a decision the designer makes *out loud*, justified by three factors: **failure cost** (what the user loses or wrongly believes if it fails), **reversibility** (can a wrong optimistic state be cleanly undone), and **latency** (is the real wait short enough that pessimistic is tolerable). Silently defaulting to one — usually optimistic because it "feels fast", or pessimistic because it's the path of least code — is precisely the failure. Mirroring `visual-hierarchy-and-type`: the skill is flexible about approach; exactly one output overrides that flexibility, and this is it. No interaction with an async surface ships without the optimistic-vs-pessimistic decision stated and reasoned.

**Focus and keyboard are first-class — "the mouse works" is half a design.** Every interactive change must state *where focus goes* and *what the keyboard path is*. When a dialog opens, focus moves into it; when it closes, focus returns to the trigger. When an async action resolves, focus lands somewhere intentional — the new content on success, the offending field on error. When an item is deleted, focus moves to its neighbour, not to nowhere. A design that specifies only pointer behaviour is not a finished interaction; it is the populated-state trap of interaction design — the easy half drawn, the half that decides whether the product is usable by everyone left blank.

**Restraint: the highest-craft interfaces move less, and only where it means something.** More motion is not more craft — it is the Vercel/Geist lesson inverted into slop. Every added transition is a claim on the user's attention that must be earned by communicative purpose; an interface where everything eases, fades, and slides is noise wearing the costume of polish. The disciplined minimum — motion only where it makes a state change legible, and nowhere else — is the craft. Over-animation reads as machine-made exactly because it is the unreviewed default of someone who believes motion *is* polish. It is not. Communicated intent is.

## Process

1. **Identify the interaction and its surface.** Name the action and the async / state-change / focus-change it triggers. What changes, when, and is there a wait between the user's act and the system's confirmation?
2. **Make and STATE the optimistic-vs-pessimistic choice.** Decide explicitly, and write the reason in terms of failure cost, reversibility, and latency. If you have not written this sentence, the interaction is not designed — this is the non-negotiable core, not a step you may skip because the skill is flexible.
3. **Specify the focus move and keyboard path.** State where focus goes on the action, on success, and on error; state how the interaction is reachable, confirmable, and recoverable from the keyboard alone. "Mouse works" is not an answer here.
4. **Give every proposed motion a communicative purpose — or cut it.** For each animation/transition, write the state change or system status it makes legible. Any motion you cannot complete that sentence for is decoration: cut it explicitly, do not keep it "because it feels nice". A stated purpose is real only if removing the motion removes a signal the user has no other way to receive — if the button state, a value updating, or a state already surfaced by `designing-states-not-screens` already conveys that information, the motion is decorative regardless of the sentence written, and is cut.
5. **Check restraint.** Re-scan the surviving motion. Is any of it redundant with another signal, or present only for feel? Remove it. Apply the redundancy discriminator: if another affordance already carries the same signal, the motion is decorative even if a purpose sentence was written for it — cut it. The disciplined minimum is the target, not the maximum the framework allows.
6. **Anchor contested calls.** Route any disputed motion, depth, or perceived-performance judgment to `design-judgment-references` (Rauno) rather than settling it by taste.

## Red flags

| Rationalisation | Reality |
|---|---|
| "Add a nice fade/animation here, it'll feel polished." | Polish is communicated intent, not movement. State what state change or system status the motion makes legible, or cut it — "feels polished" is the symptom this skill names, not a justification. |
| "I'll just add a spinner." | Spinner vs skeleton vs optimistic update is a perceived-performance decision. Which one, and why — in terms of failure cost, reversibility, and latency? A reflexive spinner is the abdication, not the answer. |
| "Mouse interaction works, that's enough." | Keyboard path and focus move are the other half of the interaction. State where focus goes on action/success/error and how the keyboard reaches and recovers it, or the interaction is half-designed. |
| "It's a flexible skill — I don't need to decide optimistic vs pessimistic." | That decision is the non-negotiable core. Flexible governs *how* you design the interaction, never *whether* you make and state this choice. Skipping it is the named FAIL. |
| "More transitions everywhere will make it feel premium." | The highest-craft interfaces move less. Every transition without a communicative purpose is noise costumed as polish; over-animation is the unreviewed slop default, not the premium one. |
| "The fade does communicate something — it tells the user the save completed." | A purpose is real only if removing the motion removes a signal nothing else carries. If the button state, a value updating, or a state already shown by `designing-states-not-screens` already says "saved", the fade is decorative — cut it. |
| "The animation is obviously fine, I don't need a reference for it." | Contested aesthetic-motion calls are anchored to `design-judgment-references` (Rauno), not settled by taste. |
