# The Linear Method — Distilled

Source: Linear, "The Linear Method" (linear.app/method). The reference for the craft/quality bar and opinionated-defaults posture.

Cite as: `linear-method.md` <principle name>.

- **Quality as recovered craft — "the lost art of building quality software".** Quality is not a finishing pass; it is the point. Software has drifted toward shipping fast and unpolished; the Linear posture is that craft and attention to detail are a deliberate, recoverable discipline, not a luxury. A "good enough, ship it" rationalisation is the exact failure this principle names.
- **Write issues, not user stories.** Describe the actual problem or task directly and concretely. Ceremony-laden "As a <role> I want <thing> so that <benefit>" templates obscure the real work; state what is wrong and what should be true.
- **Opinionated software / strong defaults.** Make decisions for the user. A tool that offloads every choice as a configurable option has pushed its design work onto the user. The default should be the right answer for most people; configurability is not a substitute for a considered default.
- **Build for the people who do the work.** Design for the practitioners actually using the product daily, not for buyers, demos, or hypothetical edge personas. The primary user is the person in the tool every day.
- **Speed and responsiveness as a core feature.** Performance is not a non-functional nice-to-have; latency is a UX defect. Instant feedback and a fast interface are part of the product's quality, judged as seriously as layout or copy.

## When to anchor here

Use Linear when the finding is about **the quality/craft bar, missing opinionated defaults (death by configuration), designing for the wrong user, or latency/responsiveness treated as out of scope**. "This punts the decision to the user instead of having a default" and "this sluggish interaction is a real defect" are Linear-anchored findings, not preference.
