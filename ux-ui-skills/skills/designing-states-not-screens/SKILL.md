## Doctrine

**The state inventory is the deliverable, not the screen.** What you owe is not "a design of this view" — it is the enumerated set of states this specific surface can be in, each one designed. The required inventory is fixed: **empty, loading (including skeleton), partial / streaming-incomplete (some data shown, more still arriving), error, edge/over-limit, first-run vs returning, offline/stale.** A view is incomplete *by definition* until every applicable state in that list is designed. "I designed the screen" is not a finished claim; "I designed each of its states" is. A surface that exists only in its populated form is not a v1 of that surface — it is a v0, missing the states users actually live in.

**The happy path is the trap — state the inversion explicitly.** The populated state is the easiest one to design and the one users live in least. Users are *empty* on day one, *erroring* on a bad day, *loading* on every single day, and *populated* only once everything has gone right. Designing only the populated state is designing for the one condition that needs the least design help and skipping the conditions that need the most. The ease of the happy path is exactly why it is the trap: it feels like the design is done because the easy 80% looks finished, while the hard, high-stakes 20% — the states that decide whether the product feels crafted or slopped — was never drawn. This is the single sharpest slop→craft differentiator: world-class UI designs every state; slop designs the populated one and calls it done.

**Empty is onboarding, never a blank.** The empty state is the highest-leverage teaching moment the product has — it is the first thing a new user sees, before any data exists to distract them. Treating empty as "hide the section" or a bare void throws away the one screen where you have the user's full attention and nothing competing for it. The Notion lesson is the canonical proof: Notion's empty pages are not blank — they onboard, demonstrate, and invite the first action, which is a primary reason the product feels craftful from the first second. An empty state that teaches nothing is a shipped bug, not a neutral default.

**Anchor to Nielsen H1 (visibility of system status) via `design-judgment-references`.** The unifying principle behind the whole inventory is that the user must *always know which state they are in*. Loading must look like loading (not like empty); error must look like error (not like a stuck spinner); stale/offline must announce itself (not silently lie with old data). Cite H1 through `design-judgment-references` — do not restate the heuristic from memory. Every state you design is verified against one question: can the user tell, unambiguously, which state this is?

**Ownership boundary — state it explicitly and hold it.** This skill owns **which states exist and that each one is designed**. It does **not** own the copy or the number/date/value formatting *inside* those states — that is owned by `precision-copy-and-formatting`. You name what each state must *accomplish* — its job (e.g. "the empty state must orient a first-time user and offer the single next action") — NOT the words it uses, not even provisionally. Designing the empty state means deciding it is an onboarding moment with an illustration, a heading, and a primary action; it does **not** mean writing the headline string or the CTA wording. Producing a draft headline/body/CTA, however labelled ("provisional", "handoff hint", "for reference"), is `precision-copy-and-formatting`'s output, not a design decision: the seam is content-existence vs content-itself, not draft vs final. Conversely, do not let the copy skill decide *whether* an empty or error state exists; that decision is owned here. Both failures are real: authoring any copy here (provisional or final) usurps the copy skill; ceding state existence there drops states. Keep the seam clean in both directions.

## Process

1. **Identify the surface.** Name the exact view/list/form/data surface being designed. One surface at a time — its state set is specific to it.
2. **Enumerate every applicable state from the inventory for THIS surface.** Walk the full inventory — empty, loading (including skeleton), partial / streaming-incomplete (some data shown, more still arriving), error, edge/over-limit, first-run vs returning, offline/stale — and for each, state whether this surface can be in it. Any state you exclude must be justified as **genuinely impossible** for this surface, not merely unlikely. "It's basically always populated in practice" is an unlikely-not-impossible argument and is rejected: design that state or prove it cannot occur.
3. **Design each applicable state, empty-as-onboarding.** Produce a design for every state that survived step 2. The empty state is designed as an onboarding moment (what is this, why is it empty, what is the one next action), never as a hidden section or a blank.
4. **Delegate copy and formatting of each state to `precision-copy-and-formatting`.** Mark the microcopy and the value/number/date formatting of each state as owned downstream. Hand off each state's *job* — what it must accomplish — not its words: no provisional strings, no draft headline/body/CTA, however labelled. You decide the state exists and what it must accomplish; the words are produced downstream.
5. **Verify against Nielsen H1 via `design-judgment-references`.** For each designed state, confirm the user can unambiguously tell which state they are in. Cite H1 through `design-judgment-references`; do not restate it from memory. A state the user cannot distinguish from another is not done.

## Red flags

| Rationalisation | Reality |
|---|---|
| "The happy path is enough for v1, we'll harden the rest later." | Users live in the non-happy states — empty on day one, error on a bad day, loading every day. A build that only has the populated state is not a v1, it is a v0; the inventory is the deliverable, not the populated screen. |
| "Empty just means hide the section / show nothing." | Empty is the single highest-leverage onboarding moment — full attention, nothing competing. A blank teaches nothing and ships as a bug. Design it the way Notion designs empty pages: it onboards. |
| "I'll add the loading and error states later." | 'Later' is precisely where unstated states become shipped blanks and stuck spinners no one drew. Enumerate and design them now; there is no later in which an undesigned state behaves well. |
| "This list is always populated in practice, so empty doesn't apply." | 'Always' is the assumption that ships the empty-state bug — new accounts, filtered-to-zero, failed loads all produce it. Design the state or prove it genuinely impossible; 'unlikely' is not 'impossible'. |
| "I'll just write the empty-state headline and error message while I'm here." | Copy and formatting are owned by `precision-copy-and-formatting`, not here. This skill owns that the state exists and what it must do; writing its final words here usurps the copy skill and blurs the seam. |
| "I'll just sketch provisional copy as a handoff hint." | A provisional draft is still the copy skill's artifact. Hand off the state's job — what it must accomplish — never its words, even labelled provisional. |
| "Loading and empty can share one neutral filler block, close enough." | Nielsen H1: the user must always know which state they are in. Loading that looks like empty (or error like a stuck spinner) is an H1 violation — verify each state is unambiguously distinguishable via `design-judgment-references`. |
